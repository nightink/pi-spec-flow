# 项目治理 Profile：为 example-app 狗粮接入保留本地权威

- 状态：已完成

## 背景与已观察事实

example-app 已有成熟且受 `AGENTS.md`、`specs/0.spec-meta.md` 和 `npm run verify` 约束的本地治理：

- spec ID 是数字，文件名为 `N.title.md`；
- 状态机是 `draft → in-review → approved → in-progress → done → archived`；
- 依赖、评审和更新时间字段分别为 `depends_on`、`reviewers`、`reviewed_at`、`updated`；
- spec 正文没有 spec-flow 的 `- 状态：…` 行；
- 权威门禁是 `npm run verify`；
- 已有多个历史 `in-progress` spec，不能因安装新工具而被强制迁移或清空证据。

只读探测还确认当前 spec-flow：

1. `findSpec("47")` 无法命中 `specs/47.sdk-session-summary.md`；
2. 只识别 `deps`、`review.decision` 和四个固定状态；
3. 只发现 example-app 的 `typecheck + vitest`，没有选择权威 `verify`；
4. 46 份 example-app spec 中 9 份 frontmatter 不是严格 YAML，当前解析为未纳管；该数据卫生问题应由后续 example-app onboarding 修复，不能靠宽松解析掩盖。

## 用户可观察结果

项目可以通过根目录 `.spec-flow.json` 显式声明自己的生命周期字段、状态角色和权威 npm 门禁。spec-flow 在该项目中保持项目原有 metadata/status 语义，同时只对显式进入 workflow v2 的 spec 执行严格证据闭环。没有配置的项目行为必须与 S1.3 完全一致。

## 非目标

- 本 spec 不修改 example-app 仓库，不迁移其 46 份历史 spec，也不关闭任何 example-app 既有 in-progress 工作。
- 不为 example-app 名称、路径或 Spec 0 写硬编码分支。
- 不执行配置文件中的任意 shell、JS 模块或可执行路径；自定义门禁只允许引用当前 `package.json#scripts` 中的 npm script 名。
- 不放宽 YAML 解析，不替项目修复无效 frontmatter。
- 不实现多仓库 snapshot/audit、任务级 snapshot 或 Windows 支持。
- 不声称 `spec_impl` 覆盖 autonomous-delivery 发现的全部真实接受面；secret scan、浏览器/设备/服务接受仍由交付编排补齐。

## 不变量与安全边界

1. **默认兼容**：缺少 `.spec-flow.json` 时，状态、字段、门禁、legacy 矩阵和正文状态行行为与当前版本逐字义等价。
2. **本地权威显式化**：profile 只能来自项目根内的普通 `.spec-flow.json`；非法 JSON、未知版本、未知键、冲突状态角色、越界/符号链接配置均 fail closed，不静默回退默认值。commit interceptor 将预期的 profile 错误转成红门禁；仅显式 `SPECFLOW_BYPASS=1` 可放行，意外的 interceptor 内部故障仍沿用 S1.1 fail-open。
3. **无任意执行面**：profile 门禁仅是 npm script 名；执行仍使用 argv `npm run <name>`，脚本不存在即配置错误。
4. **证据边界**：profile/config 是实现仓库 snapshot 的一部分；配置在 impl 后变化会使 audit/done 拒绝旧证据。v1 配置项目只允许 same-repository implementation，外部 `impl.repo` fail closed，避免 profile 语义落在 snapshot 之外。
5. **合同稳定性**：profile 声明的生命周期 metadata（如 `updated/reviewers/reviewed_at`）不进入 contract hash；依赖、目标、设计、验收、evidence 等仍进入。
6. **渐进采用**：`external-warning` 只能作用于配置中逐项列出的历史 active spec ID；未列出的 legacy active（包括删除 `workflow_version` 的未来 spec）仍 fail closed。只有显式 v2 active spec 才接受 impl/audit/attest/done。默认 profile 继续对全部 legacy active fail closed。
7. **字段隔离**：配置字段除语法安全和互不冲突外，不得占用 `id/status/workflow_version/impl/audit/attestations/evidence/scope/review` 等 spec-flow 保留键。
8. **严格内容**：配置不会把无法由 `js-yaml` 解析的 frontmatter 当作已纳管；CI 继续报告这些文件。
9. **项目状态保持**：生命周期写回使用 profile 的 active/done 状态和可选 updated 字段；关闭正文状态行同步时不得插入项目没有的状态行；proposal approval 在每个生命周期阶段仍须有效。

## 设计

### A. `.spec-flow.json` v1

首版采用严格、窄化的 schema：

```json
{
  "version": 1,
  "lifecycle": {
    "preReview": ["draft", "in-review"],
    "startable": ["approved"],
    "active": "in-progress",
    "done": "done",
    "ignored": ["archived"],
    "dependenciesField": "depends_on",
    "updatedField": "updated",
    "bodyStatusLine": false,
    "legacyActive": "external-warning",
    "externalActiveIds": ["7", "8"],
    "approval": {
      "reviewersField": "reviewers",
      "reviewedAtField": "reviewed_at",
      "minimumReviewers": 1,
      "placeholderReviewers": ["pending"]
    }
  },
  "gates": {
    "mode": "replace",
    "npmScripts": ["verify"]
  }
}
```

默认 profile 在内存中表达现有 `pending/approved/in-progress/done`、`deps`、`review.decision=approved`、正文状态行开启、legacy active error 与自动门禁发现，不要求项目新增配置。

Schema 只接受上述已定义字段。状态角色不得重叠；字段名只允许单个安全且非保留的 frontmatter key（`[A-Za-z_][A-Za-z0-9_-]*`），不支持路径表达式或原型键。`legacyActive=external-warning` 时 `externalActiveIds` 必须非空、规范化后唯一；只有列出的 ID 可走兼容 warning。`gates.mode` 首版只支持 `replace`，`npmScripts` 必须非空、去重且全部存在。

### B. 生命周期适配层

引入纯函数 profile API，集中提供：

- ID 规范化与查找（frontmatter 数字/字符串统一按字符串比较，并支持 `N.` 文件名前缀）；
- 状态角色判断和显示；
- dependency 字段读取；
- proposal approval 判断；
- lifecycle metadata 排除集合；
- active/done/updated 写回；
- 正文状态行是否同步；
- legacy active 的 CI 策略。

`begin/impl/audit/attest/done/checkCI/nextStep/renderBoard/renderSpecDetail` 不再各自硬编码这些差异。

### C. 门禁适配

`detectProjectConfig()` 在 profile 指定 gate scripts 时：

- 从当前项目 `package.json` 验证 script 存在；
- 生成固定 argv `npm run <script>`；
- `replace` 模式不再额外自动探测 typecheck/test/biome/vitest；
- 保持 gate cache、取消、输出上限和默认关闭缓存的现有语义。

配置无效不得退回较弱门禁。

### D. example-app-shaped 接受夹具

真实 CLI E2E 在临时 Git 项目构造 example-app-shaped profile/spec：数字 ID、`N.` 文件名、`depends_on`、reviewers、无正文状态行、历史 draft/archived/legacy active、新 v2 spec 和 `verify` npm script。完整验证：

1. board/findSpec 正确；
2. 历史 spec 不被迁移；
3. begin 只接受真实评审元数据；
4. impl 只运行 `verify`；
5. audit 使用隔离 fake auditor 并绑定 profile/config snapshot；
6. done 保持 example-app metadata、写 updated 且不插入状态行；
7. 配置变更使旧 evidence 失效；
8. 默认 profile 回归不变。

## Review 与决策

### Parent-only proposal review（2026-09-21）

- **采用声明式 profile，不采用 example-app 硬编码或动态项目插件**：前者可测试、可 fail closed，后两者会扩大执行与供应链边界。
- **严格 YAML 不降级**：example-app 的 9 份旧 frontmatter 是独立数据卫生债，宽松解析会制造双解析器事实源。
- **默认行为冻结**：所有渐进采用能力必须显式 opt-in，避免削弱 S1.2 的 legacy active 拒绝语义。
- **Parent diff review 加固**：blanket `external-warning` 会允许删除 `workflow_version` 后绕过 CI，已改为 explicit ID allowlist；profile 字段同时拒绝覆盖核心保留键，并在 impl/audit/attest/done 重验 proposal approval。
- **权威门禁只允许 npm script 引用**：足以覆盖 example-app `verify`，同时避免配置新增任意 argv/shell 执行面。
- **不在本 spec 修改 example-app**：spec-flow 尚不支持多仓库 snapshot；跨仓混合 diff 会使证据边界不可信。适配器完成后另立 example-app onboarding spec。
- **Reviewer 边界**：proposal 采用 parent fallback；实施完成后用户已明确授权最多两次独立模型调用（首次 audit + 必要的一次 closure re-review），不得超额或把 parent review 冒充独立证据。
