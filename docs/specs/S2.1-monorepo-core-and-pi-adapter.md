# Monorepo split: harness-neutral core npm package and Pi adapter package

## Outcome

- Restructure the repository as npm workspaces with packages/core (publishable @nightink/spec-flow-core exposing the engine API and a spec-flow CLI bin) and packages/pi (Pi extension entry, host glue and skills), while the private root package remains the git-installable Pi package.
- Eliminate path lookup for capabilities: engine modules are imported by package name inside the adapter, and target projects invoke the published CLI instead of locating core.mjs by filesystem path.
- Decouple review execution from the Pi harness behind an explicit serializable executor contract, with a bundled reference pi-cli executor, adapter injection, and an executor module selected by absolute path for other harnesses.
- Preserve current behavior and evidence semantics (gates, review protocol v3, immutable budgets, durable jobs) while making the core package publish-ready and installable by npm.

## Non-goals and safety boundaries

- No npm publish, git push, tag or release in this delivery; the package scope/name is prepared for the user to publish.
- No review protocol version bump, budget reset, or change to sealed-packet, hash or cache semantics.
- No implementation of a second harness adapter; only the contract, injection point and package template that future adapters follow.
- No rewrite of historical specs/reviews, retained evidence, or the autonomous-delivery skill workflow semantics.
- No root-level core.mjs compatibility shim: path-based invocation is replaced by the package CLI and documented migration.

## Design

- Root becomes a private npm workspace and keeps the Pi package manifest (extensions -> packages/pi/index.ts, skills -> packages/pi/skills) so pi install git:... still loads the extension and skill from the repository checkout.
- packages/core owns core.mjs, review-engine.mjs, review-coverage.mjs, review-execution.mjs, review-storage.mjs, review-worker.mjs, project-profile.mjs, workspace.mjs, spec-creation.mjs and templates/, with exports subpaths, bin spec-flow, engines and files metadata; it has no dependency on the Pi SDK, typebox or any harness package.
- packages/pi owns index.ts, adapter-core.mjs and skills/, declares @nightink/spec-flow-core as a normal semver dependency plus host peerDependencies, and imports the engine by package specifier; npm workspaces links it during git installs.
- review-execution.mjs keeps timeout/describe helpers; a new review-executor.mjs defines the contract loadReviewExecutor/resolveInvocation, validates executor modules, and defaults to the bundled executors/pi-cli.mjs reference executor which owns SPECFLOW_AUDIT_BIN, SPECFLOW_REVIEW_CLI, legacy SPECFLOW_PI_CLI and the Pi argv flags.
- runPreparedReview resolves the executor and a fully serializable invocation (bin, prefixArgs, args) before spending budget, stores it in job.execution, and the worker spawns exactly that invocation with the sealed packet as the final @file argument, removing the temporary prompt copy and its cleanup.
- A non-Pi adapter supplies its own executor module (absolute path via SPECFLOW_REVIEW_EXECUTOR or options.executor) without changing engine, worker or receipt code.
- Root keeps the test suites, E2E harnesses and shared devDependencies but imports core modules from packages/core/src; action.yml, lint/typecheck scripts, action tests, README and package docs are updated to the new layout.
- packages/core is published as @nightink/spec-flow-core 0.3.0 with publishConfig access public, exports for the engine/review/profile/executor entry points, and npm pack contents limited to src, templates and README.

## Ordered implementation plan

1. Scaffold npm workspaces: create packages/core and packages/pi package manifests, move core modules/templates and Pi adapter files/skills with git mv, and update the root Pi manifest plus package exports/peers/dependencies.

3. Extract the review executor contract and the pi-cli reference executor; serialize the invocation into job.execution; rework review-worker.mjs to consume it and use the sealed packet as the @file input; thread options.executor through review/audit.
