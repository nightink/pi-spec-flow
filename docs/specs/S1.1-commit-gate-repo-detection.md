# S1.1 提交门禁按实际提交仓库裁决，而非会话 cwd 项目

- 状态：进行中
- 规模：S
- 依赖：无
- 编制依据：2026-08-14 真实拦截案例（见 §案例）

## 目标

1. `git commit` 门禁的项目判定，从「会话 cwd 项目」改为「commit 命令实际作用的仓库」：解析命令中的 `cd <other>` 与 `git -C <other>`，或对含 `git commit` 的命令先 `git rev-parse --show-toplevel` 定位目标仓库
2. 目标仓库无任何门禁（如无 `package.json`）时直接放行，不受会话项目门禁牵连
3. bypass 台账记录实际提交仓库（`targetRepo` 字段），不再一律写进会话项目根目录
4. 保持 `SPECFLOW_BYPASS=1` 显式兜底机制不变；补台账字段与对应测试

## 案例（2026-08-14 实录）

- 会话 cwd：`~/git/github.com/<org>/<repo>`（有 `package.json`，门禁 = `npm run typecheck` + `npx vitest run`）
- 实际提交：`~/git/github.com/<user>/<user>.github.io`（GitHub Pages 静态站，无 `package.json`、无任何门禁），命令形如 `cd <pages> && cp … && git add … && git commit … && git push`
- 拦截结果：整个 tool_call 被 block，理由 `spec-flow: 门禁未通过，禁止 commit`；失败门禁为 dsh 的 typecheck / vitest，且失败原因是会话沙箱内未安装依赖（`sh: tsc: command not found`、`sh: vitest: command not found`）——环境缺失，既非目标仓库门禁、也非真实测试失败
- 处理方式：改用文档化的 `SPECFLOW_BYPASS=1` 前缀放行；台账落进 dsh 仓库 `.spec-flow-ledger.jsonl`（bypass 条目含 gates 快照与命令原文），但台账归属仓库同样不准——commit 实际发生在 pages 仓库

## 现状问题

1. **门禁用错项目**：`commitGateAction` 的 `gateResults` 来自会话 cwd 的 `detectProjectConfig`，与命令内 `cd` / `git -C` 指定的实际仓库无关。跨仓库提交必被误拦（若会话项目门禁红）或误放（若会话项目门禁绿而目标仓库有门禁）
2. **零门禁仓库不豁免**：即使目标仓库 `detectProjectConfig` 结果为空（无 `package.json`），也会被会话项目门禁拦截
3. **台账归属错误**：bypass 事件 append 到会话项目根目录，而不是实际提交仓库
4. **匹配面偏窄（次生）**：`COMMIT_RE` 只匹配 `git commit` 相邻写法，`git -C <repo> commit` 不命中——既不拦截也不台账，等于静默绕过无记录

## 期望行为

- 门禁裁决以「commit 实际目标仓库」为准：
  - 目标仓库 == 会话项目 → 现行行为不变
  - 目标仓库 != 会话项目且其自身无门禁 → 放行（建议台账记 `allow-external`，至少不 block）
  - 目标仓库自身有门禁 → 尽可能在目标仓库目录运行其门禁；无法运行时保守 block 并在 reason 里写明是哪个仓库的门禁
- 台账条目增加 `targetRepo` 字段；bypass 台账写目标仓库（无写权限时退回会话项目并标记）
- `SPECFLOW_BYPASS=1` 语义与台账不变，仅补 `targetRepo`

## 验证

- 单测（`node --test core.test.mjs`）新增用例：
  - `cd /tmp/no-pkg && git commit …` 在会话项目门禁全红时 → allow（目标仓库无门禁）
  - `git -C /tmp/no-pkg commit …` 与上等价，且进入台账/计数路径，不再被 `COMMIT_RE` 漏掉
  - `git -C <带门禁仓库> commit …` → 运行该仓库门禁而非会话项目门禁
  - `SPECFLOW_BYPASS=1` 各形态仍正确识别（含 `-C` 形态）
- 手工复现原案例：在 dsh 会话内向 pages 仓库提交，不再出现 dsh 的 typecheck/vitest 拦截

## 备注

- 实现时留意 pi 扩展宿主对 bash tool_call 的拦截点（command 字符串在进入 shell 前可拿到，`git rev-parse` 需宿主代为执行或对命令文本做最窄解析）
- 本 spec 落于扩展自身仓库 `docs/specs/`，与 dsh 等采用项目解耦
